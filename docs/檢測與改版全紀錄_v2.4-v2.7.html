一句話版本：v2.6 沒有重寫引擎，而是補上「涵蓋範圍」與「失敗時說得出話」這兩件事—— 並且用「新判定 ∪ 舊判定」的保底設計，確保任何一張表都不會比 v2.4 漏得更多。

0先說三件事

給原始程式作者的開場。

第一，引擎的核心是對的

鹽值用 secrets.token_hex(16)、代碼用 SHA-256、對照表累加、專案隔離、--decode、 .xls→.xlsx、重跑冪等——這些第一輪就逐項實測通過，v2.6 全部沿用，沒有重寫。 示範專案「4 檔／69 格／17 人」的數字，v2.6 跑出來和使用說明承諾的一模一樣。

第二，問題集中在兩件事，而且會互相放大

1. 涵蓋範圍——有好幾條路徑會讓真名與個資原封不動進入 output， 而 output 是工具向使用者保證「可以上傳」的資料夾。

2. 失敗時的訊息——真名沒被處理時，畫面顯示的是中性的灰字 （「原樣複製」「未偵測到姓名欄位」）甚至直接說「完成」。承辦同仁沒有任何線索可以察覺。

單獨看，第 1 點是「漏做」；加上第 2 點就變成 「漏做而且沒有人會發現」。v2.6 的所有改動都可以歸到這兩條線上。

第三，每一條都實跑過兩個版本

改版說明的每一條都附 檔案:行號 與實測輸出，可以自己重現。 我們沒有改動你那份 v2.4——全程唯讀，測試前後以 md5 確認未變。

1整個過程是怎麼走的

兩天、六個階段。每一次修改後都由互相隔離的代理人重新驗證，不採信自己的說法。

09-14　第一階段
實機安裝、照使用說明實際操作一次

先確認「正常情況是好的」，避免把工具本來就對的行為誤報成問題。引擎核心功能逐項實測通過。

09-14 ～ 09-15　第二階段
六組獨立稽核 ＋ 對抗式複查

六組代理人各拿一份互相隔離的乾淨副本，自己設計測試、互不知道對方的發現； 另一組代理人的任務是「推翻」前者的每一條結論。只有被攻擊後仍站得住的，才寫進報告。

09-15　產出
17 條問題回報單（P0 ／ P1 ／ P2 ／ P3）

依「會不會造成真名外洩」與「使用者能不能察覺」排序。其中 13 條的形狀完全一樣： 工具沒做到某件事，而畫面上沒有任何可以察覺的差別。

09-15　第三階段
v2.5：第一次修正，獨立驗證未通過

修完之後由獨立代理人驗證，結果不通過——判定為不可交付，不對外釋出。 這一步保留下來的意義是：「改完了」不等於「改對了」，要有人去量。

09-15 ～ 09-16　第四階段
v2.6：五輪「修 → 獨立驗證 → 再修」

三次完整的獨立驗證，每個面向一位驗證員（自己寫產生器、自己做標註集，不准看主控端的量尺）， 再配一位對抗式複查員。第三次驗證找出的每一條反例，都被做成可重複執行的回歸測試。 第五輪的每一段修改都寫成可重現的修補腳本（42 支）。

09-16 09:03　定版
v2.6 通過驗收、打包交付

673 個回歸案例通過 669 個；13,000 張隨機表格的差異測試中， v2.6 沒有任何一張的真名殘留多於 v2.4。四個未通過的案例是刻意保留的已知限制，已寫進使用說明。

2改版時只守四條原則

看到取捨就照這四條決定，不臨時發明標準。

寧可少做，不要做錯

不確定的時候，換碼優於清空、提醒優於硬做。

例：判定不到表頭時，姓名欄照樣換碼（可用 mapping 還原），但不會整欄清空。

沒處理好就不准說「完成」

任何異常都要讓視窗說「未完全成功」。

例：新增 _problems()，把引擎回傳的每一個異常統計欄位都轉成一句人話。

不比舊版少做

新判定只能增加處理範圍，不能取代舊判定。

例：保留 v2.4 的「單一標題列、整欄處理到表尾」當保底判定，與新的多段判定取聯集。

會毀資料的事先停下來

對照表／鹽值有疑慮時，寧可不處理。

例：鹽值和對照表對不上、mapping.csv 被存成 ANSI 而姓名變「?」時，一個檔都不處理。

第三條特別重要。v2.6 的表頭判定寫得比 v2.4 複雜很多，一旦判斷錯就可能比 v2.4 還糟。 所以每一格的最終判定是「新的多段判定 ∪ 舊的單列判定」—— 13,000 張隨機表格的差異測試裡沒有任何一張的真名殘留多於 v2.4，就是靠這個保底。

3我們怎麼確認「改對了」

九類測試方式。設計重點是：不讓量尺被自己調整、不讓同一套思路重複犯同一個錯。

1實機安裝＋手動實跑

解壓原始 zip、照使用說明操作視窗與示範專案。

先確認「正常情況是好的」，避免把工具本來就對的行為誤報成問題。

2獨立稽核代理人

6 組代理人各拿一份互相隔離的乾淨副本，自己設計測試。

避免同一套思路的盲點；互不知道對方的發現。

3對抗式複查

另一組代理人的任務是「推翻」前者的每一條發現。

只留下被攻擊後仍站得住的結論；反駁失敗才列入報告。

4差異模糊測試

程式隨機產生表格，同一張同時餵 v2.4 與 v2.6，逐格比對。

用量取勝：人想不到的版型由機器窮舉；門檻是「v2.6 殘留不得多於 v2.4」。

5寫實版型測試

依研發處實際檔案型態手工設計 220 個案例（計畫清單、核銷清冊、簽到表、人事異動、表單匯出…）。

模糊測試的隨機表格不等於真實表格，兩者互補。

6獨立標註集量測

先由未讀過程式的代理人標註 310 個欄名（檔案記錄「標註早於讀程式」），再量誤報率與漏報率。

防止量尺被程式反向調整——標註集一旦拿來調程式就不再獨立。

7視窗實際驅動

用 after()＋mainloop() 真的跑 GUI，把對話框換成記錄器。

視窗的錯誤（說「完成」、按鈕沒擋、搬移刪檔）只有真的跑才看得到。

8回歸測試套件

把每一條反例做成可重複執行的案例（673 案、7 個面向）。

每修一批就全跑一次，確保沒有把修好的東西改壞。

9效能與保真度量測

14 個大檔案例，兩版交錯各跑 3 次取中位數；output 逐格比對。

交錯執行才能排除機器負載差異；中位數避免單次抖動。

5當初回報的 17 條問題：現在怎麼樣了

17 條全部完成修正。其中 13 條的形狀完全一樣：工具沒做到某件事，而畫面上沒有任何可以察覺的差別。

所以 v2.6 除了逐條補涵蓋範圍，另外做了一件結構性的事： 引擎的訊息改用機器可判讀的前綴（!!＝失敗、!＝待確認），所有異常都進 stats， 再由新增的 _problems() 決定視窗要說「完成」還是「未完全成功」。

驗證方式：以上每一條都在沙箱對 v2.4 與 v2.6 各跑過一次獨立行程， 逐條附實測輸出。受測的 v2.4 全程唯讀，測試前後 md5 未變。

7v2.6 仍做不到的事

這些是知道、但決定不修的項目。判斷的共同原則是「不要為了多做一點而引進不可逆的破壞」。

項目現況為什麼不修
同一張表的第二段表格沒被認出來 第一段的姓名欄會一路往下套用到第二段（例如把「月支酬金」和金額換成代碼）；換到數字時畫面會提醒 要認出第二段就得放寬表頭判定，模糊測試顯示放寬後誤清空的格數會上升；換成代碼可以用 mapping 還原，清空不行
三字姓名夾在別的詞裡也會被換掉 姓名欄有「江大海」時，「長江大海的研究」會變成「長T-…的研究」 反過來只做整格比對，備註裡的「與江大海合作」就換不掉——那是外洩，比字被改掉嚴重
兩個字的姓名 句子裡不自動替換，只在前後文明確時提醒 兩字姓名與一般詞彙重疊率太高（田野、藍圖、連結），自動替換會大量誤傷
原始檔改名或換副檔名後重跑 舊檔名的 output 會留著，新舊兩份並存 工具無法分辨「這是舊版」和「這是先前批次的另一份檔」；自動刪除會毀掉別人的成果
直式表單、複雜合併儲存格 只提醒，不自動處理 這類表格的欄位語意必須由人判斷
「統一編號」這類機構層級欄位 單獨當欄名時會被整欄清空，而且不計入統計、視窗仍顯示「完成」 建議原作者一起決定要不要把清空欄再分成「個人」與「機構」兩類
效能 「姓名欄每格多人」與「每列長英文備註」兩種極端形狀約 1.6–1.8 倍 已做六批優化（每批都驗證結果不變），再壓要改架構；絕對差距約 1.2 秒

對應的回歸測試（673 案中的 4 個未通過案例）刻意保留為 FAIL， 作為「這是已知限制、不是迴歸」的標記。這些限制全部用白話寫在使用說明的「工具做不到的事」一節，給承辦同仁看。

為什麼用 Python 寫，不用批次檔

三位代理人各寫了一版批次檔並進沙箱實測，結果是：備份位置輸入框可以被 指令注入（輸入含引號的字串，& 之後的內容真的被 cmd 執行）； 最後的 DELETE 確認關卡只要輸入一個雙引號就會變成語法錯誤、整支批次檔中止； Get-FileHash 在某些環境取不到時，雜湊比對會靜默地拿兩個空字串相等而判定「驗證通過」。

這些全是 cmd.exe 的引號與剖析陷阱，在 Python 裡不存在——而這個工具本來就需要 Python。 所以改成：批次檔只負責找 Python，其餘全部用 Python 寫，雜湊用 hashlib、 路徑用 pathlib、輸入不經過 shell。

四項安全設計

設計為什麼
備份「整個工具資料夾」，不挑檔 確保備份範圍必定涵蓋刪除範圍。實測發現「只備份專案資料夾」的設計會漏掉 舊版（v1.x）留在工具根目錄的 _private，以及使用者自己放進去的檔案
逐檔比對 SHA-256，且 fail-closed 算不出來一律視為失敗，不讓「算不出來」長得像「一致」
完整移除要過四道關卡 確認 → 備份並驗證 → 刪除前再驗一次 → 手打 DELETE 再確認。 任何一關沒過一律什麼都不刪；直接按 Enter 永遠是取消
不自動移除 Python 與套件 pandas 等套件這台電腦的其他程式可能也在用，只顯示指令由人決定
